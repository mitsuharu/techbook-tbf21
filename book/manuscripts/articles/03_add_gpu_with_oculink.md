# OCuLink で GPU を増設する

ローカル LLM では、GPU の演算性能だけでなく VRAM 容量が扱えるモデルの上限を決めます。16 GB の GPU に収まらないモデルを試すため、同じ GPU をもう 1 枚追加したくなりました。これは先述のメインの検証機ではありません、しかも対象の PC は microATX の小型構成で、ケース内に 2 枚目を置く空間がありません。

そこで、PCIe を外部へ引き出す OCuLink を使い、GeForce RTX 5060 Ti 16 GB を増設しました。本章は NVIDIA GPU の事例です。Radeon 検証機とは異なりますが、外部 GPU の接続、PCIe 帯域、マルチ GPU の安定性を考える比較対象になります。元の作業記録もブログで公開しています。[^oculink-blog]

[^oculink-blog]: https://mthr.hatenablog.com/entry/2026/08/07/214317

## OCuLink を選んだ理由

対象 PC の構成は次のとおりです。

| パーツ | 構成 |
| :-- | :-- |
| CPU | <span class="nowrap">AMD Ryzen 7 7700</span> |
| RAM | <span class="nowrap">DDR5</span>　32 GB |
| 既存 GPU | <span class="nowrap">GeForce RTX 5060 Ti</span> 16 GB |
| マザーボード | <span class="nowrap">microATX</span>、<span class="nowrap">PCIe 4.0 x4</span> の空きあり |

1 枚の RTX 5060 Ti では ComfyUI を簡単に導入でき、動画生成も成功しました。しかし、約 20 GB の LLM モデルは 16 GB の VRAM に収まりません。CPU と RAM へのオフロードを増やせば動く可能性はありますが、速度が大きく低下します。

マザーボードには PCIe 4.0 x4 の空きスロットがありました。内部へ GPU を置けなくても、このスロットを OCuLink 端子へ変換し、外部ドックへ接続できます。Thunderbolt や USB4 の eGPU と比べ、PCIe を直接引き出す構成で、プロトコル変換のオーバーヘッドを抑えられます。

## 用意した機器

外付け GPU ドックは MINISFORUM DEG1 を使いました。PC 側に OCuLink 端子がないため、PCIe スロットを OCuLink へ変換する拡張ボードも追加しました。

```text
マザーボード
  PCIe 4.0 x4 スロット
        │
        ▼
PCIe - OCuLink 変換ボード
        │ OCuLink ケーブル
        ▼
MINISFORUM DEG1
  ├─ GeForce RTX 5060 Ti 16 GB
  └─ GPU 用電源
```

外部ドック側にも電源が必要です。PC 本体と外部 GPU の電源投入順、ケーブルの固定、露出した基板への接触に注意します。作業前にすべての電源を切り、ケーブルを抜きます。通電中に OCuLink を抜き差ししません。

## 最初は認識が安定しなかった

組み立て後、映像が出ない、Windows が GPU を認識しないという問題が発生しました。中古 GPU の故障も疑いましたが、別の PC では映像を出力できました。問題の範囲を、GPU 本体ではなく OCuLink の経路へ絞れます。

このとき、次の要素をひとつずつ確認しました。

1. GPU を別 PC の内部スロットへ挿し、単体で動作するか
2. 外部ドックの補助電源とケーブルが正しいか
3. OCuLink ケーブルを挿し直して変化するか
4. BIOS が PCIe スロットを認識しているか
5. リンク速度を下げると安定するか

最大速度のまま動かすことより、まず再現可能に認識させることを優先しました。

## PCIe の世代を Gen 3 に固定する

BIOS の初期設定は、PCIe の世代を自動判定する`Auto`でした。この状態では認識が不安定です。OCuLink 変換ボードを接続したスロットを PCIe Gen 3 に固定すると、安定して認識するようになりました。

PCIe 4.0 x4 から PCIe 3.0 x4 へ下げるため、理論帯域は半分になります。それでも、認識できない Gen 4 より、毎回認識できる Gen 3 の方が検証環境として有用です。モデルを VRAM へ載せた後の推論では、すべての処理が常に PCIe 帯域を使い切るわけでもありません。

ただし、この結果は特定のマザーボード、変換ボード、ケーブル、ドックの組み合わせによるものです。すべての環境で Gen 3 が必要とは限りません。問題がなければ Gen 4 を利用し、不安定な場合の切り分けとして世代を下げます。

## DEG1 側の設定

DEG1 のスイッチは、次のように変更しました。

| 設定 | 値 |
| :-- | :-- |
| DEBUG | B |
| TGX | OFF |

筆者の環境では、この設定と PCIe Gen 3 の組み合わせで GPU を認識しました。スイッチの意味や推奨値は、製品の版や接続先で変わる可能性があります。設定を変更する前に、利用している製品の公式資料を確認してください。

複数の変更を同時に行うと、どちらが効いたか分かりません。実際の検証では、ひとつ変更するたびに PC とドックの電源を切り、認識状態を記録します。

## 16 GB を 2 枚使う

GPU が 2 枚とも認識された後、LM Studio で約 20 GB のモデルを実行しました。1 枚の 16 GB VRAM には収まりませんが、モデルを 2 枚へ分割すると推論できました。合計 32 GB の VRAM によって、選べるモデルの範囲が広がりました。

ここで重要なのは、「VRAM が 2 倍なら速度も 2 倍」ではないことです。モデルを GPU 間で分割すると、レイヤーの境界でデータ転送が発生します。外部 GPU の接続は PCIe 3.0 x4 です。内部の x16 接続より帯域は狭くなります。1 枚へ収まる小さいモデルでは、分割しない方が速いこともあります。

マルチ GPU の価値は、単純な高速化より、1 枚では載らないモデルを GPU 上で動かせる点にあります。評価指標を token/s だけにせず、次も記録します。

- モデルの読み込みに成功するか
- CPU オフロードを減らせるか
- 長いコンテキストでも安定するか
- GPU ごとの VRAM 使用量に偏りがないか
- 連続実行でドライバーが停止しないか

## NVIDIA と Radeon の差から学ぶ

今回の LM Studio と GeForce 2 枚の構成は、筆者の環境で安定しました。一方、Radeon 2 枚では、同種のアプリケーションが推論途中で文字化けしたり、モデル読み込み中にクラッシュしたりしました。Ollama だけは比較的安定して動作しました。

GPU のハードウェアだけでなく、アプリケーションが同梱する llama.cpp のビルド設定とランタイムが結果を左右します。CUDA と ROCm で同じソースコードを使っていても、GPU 間の転送方法、同梱 DLL、対象アーキテクチャが異なります。

この差が、第 4 章で Windows 向け llama.cpp を自分でビルドする動機になりました。既成アプリの結果だけで「Radeon のマルチ GPU は動かない」と結論づけず、推論エンジン単体まで切り分けます。

## OCuLink を採用する前のチェックリスト

OCuLink は、空きスロットがあるだけで導入できるとは限りません。購入前に次を確認します。

- スロットの形状ではなく、電気的な PCIe レーン数
- M.2 や他スロットとの排他利用
- BIOS で PCIe の世代を固定できるか
- 変換ボード、ケーブル、ドックが対応する世代とレーン数
- 外部 GPU 用電源の容量とコネクター
- GPU とドックを安全に固定できる場所
- ケーブルを通電中に抜かない運用
- OS とドライバーが複数 GPU を認識するか
- 利用する推論アプリがモデル分割に対応するか

帯域、安定性、安全性のいずれかが目的に合わなければ、より大きいケースやマザーボードへ移す方が簡単です。OCuLink は万能な増設方法ではなく、既存 PC を段階的に拡張する選択肢です。

## まとめ

OCuLink を使い、ケース内に空間がない PC へ 2 枚目の GPU を追加できました。筆者の構成では、PCIe を Gen 3 に固定し、外部ドックの設定を変えることで認識が安定しました。帯域は狭くなりましたが、16 GB では載らなかったモデルを 2 枚の GPU へ分割できました。

この検証は、マルチ GPU の結果が GPU の枚数だけでは決まらないことも示しました。次章では、Radeon 2 枚で既成アプリが不安定だった原因を追い、GPU 間の peer copy を無効にした llama.cpp をビルドします。
