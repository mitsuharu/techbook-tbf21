# ローカル LLM 検証環境を壊さずに育てる

ローカル LLM 環境は、一度構築したら完成する製品ではありません。モデル、推論エンジン、GPU ドライバー、ROCm、PyTorch、ComfyUI が別々の周期で更新されます。ハードウェアも、GPU の追加や RAM の増設によって変わります。

更新のたびにすべてを入れ直し、偶然動く組み合わせを探していては、検証結果を再利用できません。本章では、これまでの事例を横断し、問題を層ごとに切り分ける方法、正常な基準を残す方法、更新と復旧を運用へ組み込む方法をまとめます。

## 問題を層に分ける

「生成できない」という症状だけでは、原因の範囲が広すぎます。次の層へ分け、下から順に確認します。

| 層 | 主な要素 | 最小の確認 |
| :-- | :-- | :-- |
| 1. 電源と接続 | PSU、補助電源、PCIe、OCuLink | BIOS とデバイスマネージャーで認識する |
| 2. OS とドライバー | Windows、AMD／NVIDIA ドライバー | GPU 単体の負荷テストが通る |
| 3. 計算ランタイム | CUDA、ROCm、Vulkan、PyTorch | デバイス一覧と最小計算が通る |
| 4. 推論エンジン | llama.cpp、ComfyUI | 小さい既知モデルを実行できる |
| 5. モデル | GGUF、safetensors、量子化 | 対応形式を読み込める |
| 6. API | Ollama、LM Studio、llama-server | localhost から応答する |
| 7. ネットワーク | LAN、ファイアウォール、認証 | 別端末の curl から応答する |
| 8. クライアント | Xcode、エージェント、ワークフロー | 小さい固定タスクを完了する |

下の層が失敗しているときに、上の層の設定を変えません。たとえば Xcode Agent が停止した場合、Agent のプロンプトを直す前に、curl で API を確認し、サーバー側で同じモデルを実行します。

## 正常な基準をひとつ作る

問題の切り分けには、正常に動く小さい構成が必要です。筆者は、次のような基準を用意します。

- GPU 1 枚
- 小さい GGUF モデル
- 短いコンテキスト
- `llama-cli`の既知コマンド
- 固定プロンプト
- 1 回の応答

この構成が動いた後、GPU を 2 枚にします。続いてモデルを大きくし、API サーバーへ変更します。最後に Xcode を接続します。この順でひとつずつ条件を加えます。

ComfyUI でも、低解像度、短いフレーム数、既知の`int8_convrot`モデル、固定 seed のワークフローを基準にします。最初から長い動画を生成すると、モデル読み込みと長時間カーネルのどちらで失敗したか分かりません。

## 検証マトリックスを小さく保つ

組み合わせをすべて試すと、数が急増します。2 種類のドライバー、2 種類の ROCm、3 種類の llama.cpp、4 種類のモデルだけでも 48 とおりです。目的のない総当たりをせず、現在の安定版と更新候補を比較します。

| 項目 | 安定版 | 更新候補 |
| :-- | :-- | :-- |
| ドライバー | 現在正常に動く版 | 対象 ROCm の推奨版 |
| ROCm | 7.2.1 または 7.14.0 | 10.0.0 |
| 推論エンジン | 保存済み成果物 | 更新した submodule |
| モデル | ハッシュ固定の小型モデル | 利用したい新モデル |
| クライアント | curl と CLI | Xcode やデスクトップ UI |

まず更新候補をひとつだけ変えます。新モデルが新しい llama.cpp を要求するなら、モデルと推論エンジンの 2 項目を変える必要があります。その場合もドライバーと ROCm は固定します。

## 版を 4 つの場所で固定する

再現性には、Git のコミットだけでは足りません。次の 4 か所を固定します。

### ソースコード

llama.cpp は Git submodule のコミットで固定します。ComfyUI とカスタムノードも、動作確認したコミットを記録します。`main`や`master`の最新状態だけを参照しません。

### ツールチェイン

CUDA、ROCm、Vulkan SDK、Python、PyTorch のバージョンを保存します。GitHub Actions の入力、キャッシュキー、Artifact 名にも含めます。

### モデル

配布元、リビジョン、ファイル名、サイズ、ハッシュ、ライセンスを記録します。同じ名前でファイルが更新される場合に備えます。

### 実行設定

起動オプション、環境変数、ワークフロー JSON、モデル分割、コンテキスト長、seed を保存します。`--disable-dynamic-vram`や`GGML_CUDA_NO_PEER_COPY`のような設定が抜けると、同じバージョンでも結果が変わります。

## ログを「あとから比較できる形」で残す

エラー画面の写真だけでは、あとから検索と比較ができません。実行ごとに、次をテキストで保存します。

```text
日時
PC の識別名
OS とドライバー
GPU 名、gfx ターゲット、接続幅
RAM と VRAM
Python、PyTorch、ROCm
llama.cpp または ComfyUI のコミット
モデル名、量子化、ハッシュ
実行コマンドと環境変数
標準出力と標準エラー
開始、モデル読み込み、完了の時刻
最大 RAM、VRAM、温度、消費電力
成功、失敗、手動中断の区別
```

秘密情報、API キー、機密プロンプトをログへ含めません。共有する前に、ユーザー名、ローカルパス、IP アドレスも確認します。

## 性能を 1 つの数値へ縮めない

LLM 推論では token/s、動画生成では完了までの秒数が分かりやすい指標です。しかし、更新判断には次も必要です。

- アプリケーションの起動時間
- モデル読み込み時間
- 最初のトークンまでの時間
- 長時間実行の成功率
- 最大 VRAM と RAM
- 消費電力と GPU 温度
- ドライバー停止後の復旧時間
- 必要な手作業とセキュリティ設定

ROCm 10 は動画生成を短縮しましたが、動的 VRAM を無効にし、Smart App Control の判断が必要でした。速度だけなら更新、運用全体では保留という結論もあり得ます。

## 監視と自動復旧

長時間ジョブは、人が画面を見続ける前提にしません。最低限、次を監視します。

- サーバープロセスが存在するか
- API のヘルスチェックへ応答するか
- ジョブが進行しているか
- GPU 使用率と温度が異常でないか
- 出力ディスクの空き容量があるか
- 再試行回数が上限を超えていないか

プロセスが存在しても、モデル読み込み中やハングで API が応答しない場合があります。反対に、大きなモデルの読み込みで一時的に応答が遅いだけの場合もあります。短いタイムアウト 1 回で終了と判断せず、長めの猶予と複数回の確認を使います。

自動復旧は、次の範囲に限定します。

1. 一時的な API 失敗を再試行する
2. 終了を確認したサーバーを再起動する
3. 冪等なジョブだけを再投入する
4. 上限回数で停止する
5. ログと未完了ジョブを残す

生成物の上書き、モデル削除、ドライバー再インストールを自動復旧に含めません。原因不明の状態で破壊的な処理を繰り返さないためです。

## バックアップするものと再生成するもの

数十 GB のモデルと SDK をすべて Git へ入れる必要はありません。保存対象を分けます。

| 保存する | 再取得・再生成する |
| :-- | :-- |
| セットアップスクリプト | Python 仮想環境 |
| バージョンとハッシュ | ComfyUI 本体の作業コピー |
| ワークフローとプロンプトひな型 | ROCm SDK とビルド中間物 |
| 小さい検証入力 | 公開モデルの重み |
| ビルド済みの正常な配布 ZIP | GitHub Actions のキャッシュ |
| 実測結果とログ | 再生成できる一時動画 |

公開元から消える可能性があるモデルや、自分で変換した重みは別です。ライセンスを確認し、その条件で保存を許されたストレージへ置きます。生成した作品や再作成できない入力もバックアップします。

## LAN 内サーバーの安全性

推論を LAN 内に置けば、外部のクラウドへ送信しない構成を作れます。しかし、LAN 内の全端末を信頼できるとは限りません。API が認証なしなら、同じネットワークの別端末が GPU を利用したり、モデル一覧を取得したりする可能性があります。

個人の検証でも、次を行います。

- API の待ち受けを必要なインタフェースへ限定する
- ファイアウォールで接続元とポートを絞る
- ルーターのポート転送を設定しない
- API キーを利用できる場合は設定する
- 推論ログに入力を残すか確認する
- OS とドライバーのセキュリティ更新を止めない

Smart App Control を含むセキュリティ機能と互換性がない場合は、無効化だけが解決策ではありません。古い ROCm を使う、専用 PC へ分離する、仮想環境を使う、NVIDIA／CUDA 構成へ切り替える選択肢も比較します。

## エージェントに任せる範囲

本書の環境構築では、エージェントが調査、スクリプト作成、エラー修正を支援しました。複雑な依存関係を追う作業に有効です。一方、エージェントの出力を実機で実行するのは利用者です。

次の操作は、実行前に人が確認します。

- BIOS とファームウェアの変更
- ドライバーの削除と入れ替え
- Smart App Control や Defender の設定変更
- PowerShell の実行ポリシー変更
- 管理者権限のコマンド
- 大容量モデルのダウンロード
- 外部スキルやスクリプトの導入
- ファイアウォールと API 公開設定

エージェントには、確認コマンド、期待する出力、元へ戻す手順を一緒に作らせます。「動くようにして」だけでなく、変更を小さく分け、各段階でログを確認します。

## 次に検証したいこと

本書では、環境を構築して用途へ接続するところまで進みました。比較の精度と実用性を高めるには、次の追試が必要です。

### 運用コスト

待機時、モデル読み込み時、推論時の消費電力を計測し、電気料金と利用時間から月間費用を見積もります。クラウド API と比較するときは、PC 本体の購入費と保守時間も含めます。

### バックエンド比較

同じ PC、モデル、プロンプトで CUDA、ROCm、Vulkan を比較します。対応する GPU が異なるため完全な同条件にはなりませんが、速度、導入時間、安定性、利用できるモデル形式を同じ表で評価します。

### メモリの対応表

モデルサイズ、量子化、コンテキスト長、VRAM、RAM、CPU オフロードの関係を実測します。「24 GB で動く」という情報を、どの条件でどの速度だったかまで具体化します。

### 複数ユーザー運用

API の認証、TLS、キュー、同時実行数、モデル切り替え、利用量の記録を設計します。個人用の開放ポートから、LAN 内サービスへ移行するための要件です。

### ライセンスとデータ管理

モデル、学習データ、生成物、コードのライセンスを整理します。モデルをローカルで実行しても、入力データの利用権や生成物の扱いが自動的に解決するわけではありません。

## まとめ

ローカル LLM 環境を安定して育てるには、問題をハードウェアからクライアントまでの層へ分け、正常な最小構成と比較します。ソース、ツールチェイン、モデル、実行設定を固定し、更新前後のログと性能を残します。

Windows と Radeon の組み合わせは、CUDA 前提の環境より手間がかかりました。その手間をスクリプト、Artifact、ログ、復旧処理へ変えれば、次の更新で同じ調査を繰り返さずに済みます。ローカル LLM の楽しさは、モデルを一度動かすことだけでなく、自分の用途に合わせて環境を理解し、少しずつ制御できる範囲を広げることにあります。
