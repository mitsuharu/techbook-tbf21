# Xcode からローカル LLM サーバーを利用する

Xcode 26 は AI によるコード生成を統合しました。Xcode 自身がプロジェクト構造と Swift のビルド結果を把握しているため、汎用チャットへファイルを貼り付けるより自然にコンテキストを渡せます。一方、開発用 Mac でローカル LLM も実行すると、Xcode とモデルが同じメモリと GPU を奪い合います。

そこで、前章までに構築した Windows PC を推論サーバーにします。Mac は Xcode のビルドと画面表示に専念し、LAN 経由で Windows PC の OpenAI 互換 API を利用します。本章は、iOSDC Japan 2026 のパンフレット原稿を本書向けに再編集したものです。[^iosdc-manuscript]

[^iosdc-manuscript]: 自作 PC で始めるローカル LLM を利用した Xcode のコード自動生成 https://github.com/mitsuharu/iosdc-2026-pamphlet/blob/main/manuscripts/index.md

## 検証した構成

本章の記載は 2026 年 7 月上旬の検証結果をもとにしています。Xcode と各アプリケーションの設定は更新されるため、実際の画面や対応プロバイダーが異なる場合があります。

| 項目 | 検証環境 |
| :-- | :-- |
| 開発機 | MacBook Pro 14 インチ、M5、メモリ 32 GB |
| OS | macOS 26.5.1 |
| Xcode | 26.5.0 |
| 推論サーバー | Windows 11、Radeon AI PRO R9700 32 GB × 2、RAM 128 GB |
| API サーバー | LM Studio 0.4.18、Ollama 0.31.1 |
| 主な検証モデル | Gemma 4、Qwen 3.6、Ornith 1.0 |

モデルとアプリケーション名は検証時点のものです。公開停止、改名、バージョン変更の可能性があります。接続方法を理解し、利用時点で取得できるモデルへ置き換えてください。

## なぜ別 PC へ分けるのか

MacBook Pro の 32 GB メモリは、一般的なアプリ開発には十分です。しかし、16 GB 程度の量子化モデルを読み込むと、重み、KV キャッシュ、Xcode、シミュレーターが同じユニファイドメモリを使用します。メモリプレッシャーが高まり、推論かビルドのどちらかが遅くなります。

Mac は購入後にメモリと GPU を増設できません。大容量メモリのモデルへ買い替える方法もありますが、LLM のためだけに開発機全体を更新することになります。推論用 PC を分けると、次の利点があります。

- Mac のメモリと GPU を Xcode に使える
- 推論用 PC の GPU、RAM、ストレージを後から交換できる
- モデルとプロンプトを LAN 内に保てる
- 複数の Mac やツールから同じモデルを利用できる
- 推論サーバーの更新失敗が、開発環境を直接壊さない

欠点は、PC が 2 台必要になり、ネットワークとアクセス制御を管理することです。推論 PC の消費電力と騒音も増えます。

## 先に Mac 単体で接続を確認する

ネットワークの問題とモデルの問題を分けるため、最初は Mac 上の LM Studio または Ollama を Xcode へ接続します。小さいモデルを利用し、Xcode 側の設定が正しいことだけを確認します。

LM Studio は GUI からモデルを選び、Local Server を起動できます。Ollama はターミナルからモデルを実行します。

```shell
ollama run <model-name>
```

Ollama の既定 API ポートは `11434`、LM Studio は `1234` です。別のアプリケーションが使用している場合は変更します。

## Chat にローカルプロバイダーを追加する

Xcode 26 の Chat では、ローカルでホストするモデルプロバイダーを追加できます。検証時点では、次の流れでした。

1. Xcode の Settings から Intelligence を開く
2. Add a Model Provider を選ぶ
3. Locally Hosted を選ぶ
4. LM Studio なら `1234`、Ollama なら `11434` をポートへ指定する
5. Coding Assistant のモデル選択から登録したモデルを選ぶ

この構成で、「現在の画面にカウンターを追加する」のような短い指示を試します。最初から複数ファイルの変更を依頼せず、選択範囲の説明、1 関数の生成、コンパイルエラーの説明へ段階的に進みます。

## Agent のバックエンドを変更する

検証時点の Xcode では、Chat と異なり、Agent に任意のプロバイダーを追加する画面がありませんでした。既存の Claude Agent が読む設定ファイルで、接続先を OpenAI 互換 API へ変更しました。

LM Studio を Mac 上で動かす例は次のとおりです。

```json
{
  "env": {
    "ANTHROPIC_AUTH_TOKEN": "lmstudio",
    "ANTHROPIC_BASE_URL": "http://localhost:1234"
  }
}
```

この方法は Xcode と Agent の実装に依存します。公式に保証された拡張点か、バージョン更新後も利用できるかを確認してください。設定前のファイルを保存し、戻せるようにします。

ローカルモデルは、Claude 向けのツール呼び出しやプロンプトへ十分に追従できない場合があります。Chat の応答が生成できても、Agent が正常にファイルを編集できるとは限りません。

## Windows PC で API サーバーを起動する

Mac 単体で接続できたら、モデルを Windows PC へ移します。LM Studio と Ollama には、LAN 内からアクセスできるように待ち受ける設定があります。設定名はバージョンで変わるため、次の状態を確認します。

- サーバーが Windows PC の LAN アドレスで待ち受けている
- Windows ファイアウォールで対象ポートが許可されている
- ネットワークプロファイルがプライベートになっている
- Mac から Windows PC の IP アドレスへ到達できる
- API が意図しないネットワークへ公開されていない

接続確認には、モデル一覧や小さいリクエストを利用します。エンドポイントはサーバーごとに確認してください。

```shell
curl http://192.168.100.19:11434/api/tags
```

IP アドレスを固定しない場合、DHCP によって再起動後に変わる可能性があります。ルーターの DHCP 予約を使うか、名前解決を用意します。

## Xcode を LAN 上のサーバーへ向ける

Chat では、Internet Hosted に相当する接続先として Windows PC の IP アドレスとポートを指定します。API キーを設定できるサーバーなら、推測しにくい値を利用します。

Agent の例は、`localhost` を Windows PC のアドレスへ変え、利用するモデルを指定します。

```json
{
  "env": {
    "ANTHROPIC_AUTH_TOKEN": "ollama",
    "ANTHROPIC_BASE_URL": "http://192.168.100.19:11434",
    "ANTHROPIC_MODEL": "ornith:35b"
  }
}
```

この例の IP アドレスとモデル名は検証環境の値です。そのままコピーせず、自分の環境へ置き換えます。

## LAN 内でもアクセス制御する

ローカル LLM だから安全なのではなく、自分で境界を管理できる点が利点です。認証なしの API を `0.0.0.0` で待ち受けると、同じネットワークの端末からモデルを利用できる場合があります。プロンプトの内容や生成結果をサーバーログへ残す実装もあります。

最低限、次を確認します。

- ルーターで対象ポートをインターネットへ転送しない
- Windows ファイアウォールの接続元を必要な LAN 範囲へ絞る
- 公衆 Wi-Fi ではサーバーを公開しない
- 利用しないときは API サーバーを停止する
- API キーや認証機能があれば有効にする
- ログの保存場所、保存期間、入力内容を確認する
- 組織の端末とネットワーク規則に従う

複数人で常用するなら、リバースプロキシ、TLS、ユーザーごとの認証、監査ログも検討します。本書の単一 LAN 上の検証構成を、そのまま業務用サービスにしません。

## コード生成を評価する

検証では、Xcode の Chat と Agent から同じローカル LLM サーバーを利用しました。Chat には一画面の実装を依頼し、Agent には GitHub のリポジトリを検索する小規模な iOS アプリを依頼しました。比較のため、別のローカルモデルとクラウドモデルでも実装しました。結果のコードは評価用リポジトリで公開しています。[^evaluation-repository]

[^evaluation-repository]: evaluate-local-llms-for-ios-app https://github.com/mitsuharu/evaluate-local-llms-for-ios-app

ローカルモデルは、短く明確な Chat の指示を処理できました。Agent も小規模なアプリを完成させましたが、クラウドモデルより速度と品質で見劣りします。複雑な要求を一度に渡すより、設計、1 機能の実装、ビルド、修正へ分割した方が安定しました。

評価では、「アプリが完成したか」だけでなく次を記録します。

| 観点 | 確認内容 |
| :-- | :-- |
| 正しさ | ビルドとテストが成功するか |
| 変更範囲 | 指示していないファイルを壊していないか |
| 追従性 | プロジェクト固有の規約を守るか |
| 回復性 | コンパイルエラーをログから修正できるか |
| 速度 | 初回応答とタスク完了までの時間 |
| 資源 | VRAM、RAM、GPU 使用率、消費電力 |

ローカル LLM は、生成回数の上限を気にせず試せます。その一方、誤った修正を高速に繰り返す可能性があります。Git の作業ブランチを使い、ビルドとテストを各段階で実行します。

## 失敗しやすい接続を切り分ける

| 症状 | 切り分け |
| :-- | :-- |
| Xcode にモデルが出ない | Mac 上のローカル接続、ポート、プロバイダー設定 |
| Mac から API へ接続できない | Windows の待ち受け、IP、ファイアウォール |
| Chat は動くが Agent は失敗する | ツール呼び出し、モデル指定、コンテキスト長 |
| 長い処理で停止する | サーバーログ、VRAM、コンテキスト、タイムアウト |
| Xcode が重い | 推論が Mac 側で動いていないか、メモリプレッシャー |
| 出力が途中で壊れる | 推論エンジン、モデル、マルチ GPU、量子化形式 |

まず curl など単純なクライアントで API を確認し、次に Xcode Chat、最後に Agent を試します。ネットワーク、API、モデル、Agent を一度に調査しません。

## 現実的な使い分け

検証したローカルモデルは、単純な実装支援に利用できました。しかし、主要なクラウドモデルを完全に置き換える品質ではありません。筆者は、説明、定型コード、機密性の高い小変更、クラウドの利用枠を節約する下準備に使います。複雑な設計や、長時間の自律的な変更はクラウドも利用します。

推論サーバーを分けたことで、Mac の Xcode は安定しました。代わりに、Windows 側の GPU は高い使用率になり、消費電力とファン回転数が上がります。処理を別 PC へ移しても、計算資源の問題が消えるわけではありません。置き場所を選べるようになります。

## まとめ

OpenAI 互換 API を利用し、Windows のローカル LLM サーバーを Xcode の Chat と Agent へ接続しました。開発用 Mac と推論用 PC を分けることで、Xcode のメモリを守りながら、入力を LAN 内に保てます。

次章では、同じ Radeon 検証機を LLM 推論とは別の用途へ広げます。ComfyUI と MiniMax H3 を導入し、テキストから音声付き動画を生成します。
