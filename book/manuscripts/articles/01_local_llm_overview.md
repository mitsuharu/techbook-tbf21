# ローカル LLM 環境を手元に置くということ

生成 AI は、ソフトウェア開発で欠かせない道具です。クラウド型のサービスなら、アカウントを用意するだけで高性能なモデルを利用できます。それでも筆者はローカル LLM を試します。理由はクラウドより高性能だからではありません。利用回数、接続先、モデルのバージョン、入力データの置き場所を自分で選べる環境が欲しいからです。

本章では、本書で扱うローカル LLM の範囲を定めます。クラウドとの違い、モデルを動かすための基本用語、検証環境の全体像を先に共有します。具体的な PC の設計は第 2 章から始めます。

## クラウド型 AI の便利さと制約

クラウド型 AI は導入が簡単です。大規模な GPU を自分で購入せずに済み、モデルや推論基盤の更新もサービス提供者が行います。一方で、次の制約は利用者側だけでは解消できません。

- 契約プランや一定期間ごとの利用上限がある
- API は利用量に応じた費用が発生する
- モデルの更新や提供終了を利用者が制御できない
- 推論のためにプロンプトやソースコードを外部へ送信する
- サービス障害やネットワーク障害の影響を受ける

「入力データを学習に利用しない」という設定は重要です。しかし、これは「データを外部へ送信しない」と同じではありません。顧客との契約や組織の規則によって、ソースコードや設計情報を外部サーバーへ送信できない案件もあります。ネットワークを分離した環境では、そもそもクラウドへ接続できません。

また、コード生成は長いコンテキストを繰り返し送ります。少数の質問なら気にならない利用量でも、エージェントが調査、編集、ビルド、修正を繰り返せば、短時間で上限へ達する場合があります。ローカル LLM は、このような制約に対する選択肢になります。

## ローカル LLM で得られる制御

本書におけるローカル LLM は、公開されたモデルの重みを手元の PC へ保存し、その PC の CPU や GPU で推論する構成を指します。LAN 内の別 PC から API を利用する場合も、外部サービスへ推論を依頼しないため、本書ではローカル LLM に含めます。

手元で環境を管理すると、次の項目を自分で決められます。

- 利用するモデルとバージョン
- 量子化形式とコンテキスト長
- 推論エンジンと起動オプション
- モデルと入力データの保存場所
- API を公開するネットワーク範囲
- 更新する時期と、問題発生時に戻すバージョン

モデルの重みを一度取得すれば、推論回数に応じた追加料金は発生しません。ただし、PC の購入費、電気代、保守時間は必要です。「無料の AI」ではなく、費用の発生場所と管理者が変わると考える方が正確です。

## すべてを置き換えるものではない

ローカル LLM とクラウド LLM は、どちらか一方を選ぶ関係ではありません。個人が用意できる GPU と電力には限界があります。数百 GB から TB 級の重みをもつモデルは公開されています。しかし、家庭用 PC で扱うことは困難です。小中規模のモデルも改善を続けています。複雑な推論、広い知識、長時間のエージェント処理では、クラウド上の大規模モデルが優位です。

筆者は、次のように役割を分けています。

| 用途 | 選択しやすい環境 | 理由 |
| :-- | :-- | :-- |
| 機密情報を含む短いコード補完 | ローカル | 入力を LAN 外へ出さず、繰り返し利用できる |
| 定型的な変換や要約 | ローカル | 小中規模モデルでも要求を限定しやすい |
| 最新情報を含む調査 | クラウド | Web 検索や新しい知識を利用しやすい |
| 複雑な設計判断 | クラウド | 大規模モデルの推論性能を活かしやすい |
| 大量の試行が必要な実験 | 併用 | ローカルで候補を絞り、難所だけクラウドへ渡せる |

ローカルで処理できる仕事を増やせば、クラウド側の利用枠を難しい仕事へ回せます。片方を排除するより、処理の性質に応じて使い分ける方が現実的です。

## モデルの大きさを読む

モデル名には、`9B`、`27B`、`35B`のような値が含まれます。B は Billion、つまり 10 億を表します。この値はモデルのおおよそのパラメータ数です。パラメータ数だけで性能は決まりませんが、必要なメモリを見積もる手がかりになります。

### 量子化

1 パラメータを 16 bit で保存する 32B モデルは、重みだけで単純計算約 64 GB です。家庭用 GPU に載せるには大きすぎます。そこで、重みを低いビット数で表現する量子化を利用します。たとえば 4 bit 量子化なら、重みの理論上の大きさは 16 bit の 4 分の 1 です。

実際のメモリ使用量は、重みだけでは決まりません。KV キャッシュ、コンテキスト長、実行時バッファ、推論エンジンの実装も影響します。モデルファイルが VRAM 容量に収まるという理由だけで、動作を保証できません。数 GB の余裕を持ち、実行中の使用量を計測します。

### MoE

MoE は Mixture of Experts の略で、複数の専門家に相当する部分から、入力に応じて一部を使う方式です。モデル全体のパラメータ数が大きくても、トークンごとに利用するパラメータを限定できます。計算量を抑えながら能力を高められる一方で、利用しない部分を含む重みはメモリへ読み込む必要があります。

したがって、モデルを選ぶときは総パラメータ数だけでなく、量子化後のファイルサイズ、アクティブパラメータ数、必要なコンテキスト長を確認します。

## 推論を支えるソフトウェア

本書では、主に LM Studio、Unsloth Desktop、Ollama、llama.cpp を扱います。LM Studio と Ollama は、内部の推論に llama.cpp を利用する構成を持ち、モデルの管理や API サーバーなどを使いやすい形で提供します。

Unsloth Desktop は、モデルの実行と学習を GUI から扱い、OpenAI 互換 API やエージェントとの接続も提供するデスクトップアプリです。公式サイトでは Windows、macOS、Linux に対応しています。[^unsloth-desktop] 筆者は Radeon 検証機で動作を確認し、自分でビルドした llama.cpp の動作確認にも利用しています。推論、モデル管理、エージェント連携をひとつの画面で扱える選択肢です。

| ツール | 向いている用途 | 本書での位置づけ |
| :-- | :-- | :-- |
| <span class="nowrap">LM Studio</span> | GUI でモデルを探し、設定を変えながら試す | 初期検証と <span class="nowrap">NVIDIA</span> のマルチ GPU 検証 |
| <span class="nowrap">Unsloth Desktop</span> | GUI でモデルを実行・学習し、エージェントへ接続する | <span class="nowrap">Radeon</span> と自作ビルドした <span class="nowrap">llama.cpp</span> の動作確認 |
| <span class="nowrap">Ollama</span> | CLI と API でモデルを継続運用する | Radeon 検証機の推論サーバー |
| <span class="nowrap">llama.cpp</span> | バックエンドやビルド設定まで制御する | <span class="nowrap">Windows</span> 向けビルドと問題の切り分け |

[^unsloth-desktop]: [Unsloth Desktop 公式サイト](https://www.unsloth.ai/)

これらは OpenAI 互換 API を提供できます。推論用 PC で API サーバーを起動し、開発用 Mac や別のクライアントから LAN 経由で利用できます。クライアント側はモデルを保持せず、Xcode やエージェントの処理に専念できます。

## 本書で構築する環境

本書の中心は、Windows 11 と Radeon GPU を搭載した自作 PC です。主な検証機は Radeon AI PRO R9700 32 GB を 2 枚、システムメモリを 128 GB 搭載します。GPU の価格と VRAM 容量を重視して Radeon を選びました。

ただし、すべての検証を Radeon だけで行うわけではありません。CUDA 前提のソフトウェアとの差を知るため、GeForce RTX 5060 Ti 16 GB を使った構成も扱います。OCuLink の章では、同 GPU を 2 枚に増設した事例を取り上げます。

```text
開発用 Mac（Xcode）
        │
        │ LAN / OpenAI 互換 API
        ▼
Windows 11 検証機
  ├─ Ollama / LM Studio / Unsloth Desktop / llama.cpp
  ├─ Radeon GPU × 2
  └─ ComfyUI + ROCm + MiniMax H3
```

推論、コード生成、動画生成は、必要なソフトウェアと安定性の条件が異なります。ひとつの Python 環境へすべてを詰め込まず、用途ごとに実行環境を分けます。モデルやソースコードを再取得できるようにし、Git にはセットアップ手順と設定だけを保存します。

## 本書の読み方

第 2 章と第 3 章はハードウェアを扱います。すでに PC がある場合も、VRAM、RAM、PCIe レーン、電源の確認に利用できます。第 4 章は、既成の推論アプリだけでは安定しなかった経験から、llama.cpp のビルドとランタイム配布を自分で管理します。

第 5 章では、推論環境を LAN 内のサーバーとして Xcode へ接続します。第 6 章と第 7 章は、ComfyUI と MiniMax H3 を Radeon で動かし、ROCm 10 へ更新します。第 8 章で、ここまでに現れた問題を層ごとに切り分けます。

## まとめ

ローカル LLM の価値は、クラウドより高い性能を得ることだけではありません。モデル、データ、推論エンジン、更新時期を自分で制御できる点にあります。その代わり、機材費、電力、互換性、保守を自分で引き受けます。

次章では、動かしたいモデルから VRAM と RAM を見積もり、これらの責任を引き受けられる検証機を設計します。
