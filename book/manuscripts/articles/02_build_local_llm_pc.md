# ローカル LLM 検証機を設計する

自作 PC のパーツ選びは、予算内でもっとも高性能な製品を集めれば終わりではありません。ローカル LLM では、動かしたいモデルを VRAM に載せられるか、GPU と同程度の重みをシステムメモリでも扱えるか、複数の GPU を接続できるかが重要です。さらに、電源、冷却、日常用途との共存も考える必要があります。

筆者が検証機に定めた目標は、24 GB 以下で動く定番モデルを余裕を持って扱い、32〜50 GB 程度のモデルも試せることです。それを超えるモデルは、個人用 PC だけで無理に扱わず、クラウドを選びます。本章では、この目標から各パーツを選んだ過程を説明します。構成の元になった記録は Qiita で公開しています。[^qiita-pc]

[^qiita-pc]: https://qiita.com/mitsuharu_e/items/92a3eccb65d9b5c4ceca

## モデルから逆算する

最初に GPU の製品名を決めるのではなく、使いたいモデルの量子化後サイズを確認します。モデルファイルに加え、KV キャッシュと実行時バッファの余裕が必要です。32 GB のモデルファイルを 32 GB の VRAM へ載せる設計では、条件を少し変えただけで CPU へオフロードされます。

筆者は、検証範囲を次の 2 段階に分けました。

| 範囲 | モデルの目安 | 構成方針 |
| :-- | :-- | :-- |
| <span class="nowrap">日常利用</span> | <span class="nowrap">VRAM 24 GB 以下</span> | 1 枚の GPU、または十分な余裕をもつ複数 GPU で円滑に動かす |
| <span class="nowrap">拡張利用</span> | <span class="nowrap">VRAM 32〜50 GB</span> | 複数 GPU へ分割し、速度より「動かせること」を優先する |

複数 GPU の VRAM は、すべてのアプリケーションで自動的にひとつの大きな領域になるわけではありません。推論エンジンがモデルのレイヤーを分割し、各 GPU へ配置できる必要があります。用途ごとに対応状況を確認します。

## 検証機の構成

2026 年 8 月時点の主な構成は次のとおりです。新品だけでそろえず、以前の自作 PC からの流用品、中古品、アウトレット品も利用しました。ゲーム、画像生成、動画生成との兼用機です。

| パーツ | 構成 | 選定の軸 |
| :-- | :-- | :-- |
| OS | <span class="nowrap">Windows 11</span> | 日常利用するゲームやアプリとの共存 |
| CPU | <span class="nowrap">Intel Core i5-14400</span> | 内蔵 GPU、消費電力、DDR4 対応 |
| <span class="nowrap">CPU クーラー</span> | 120 mm 級空冷 | 扱いやすさと保守性 |
| <span class="nowrap">マザーボード</span> | <span class="nowrap">ASRock B760 Pro RS/D4 Wi-Fi</span> | PCIe スロット数、DDR4、LGA1700 |
| GPU | <span class="nowrap">Radeon AI PRO R9700 32 GB x2</span> | VRAM 容量と価格のバランス |
| RAM | <span class="nowrap">DDR4</span> 128 GB | GPU へ載せるモデルと OS の作業領域 |
| ストレージ | <span class="nowrap">NVMe SSD 2TB</span> | 大きなモデルの読み込みと入れ替え |
| 電源 | 1000 W、<span class="nowrap">80 PLUS Gold</span>、<span class="nowrap">ATX 3.1</span> | GPU 2 枚と瞬間的な負荷への余裕 |
| ケース | ATX 対応、通気重視 | 2 枚の GPU の冷却と作業性 |

## OS とバックエンドを先に考える

Radeon の計算基盤である ROCm は、Linux の対応範囲と情報量が充実しています。それでも筆者は Windows 11 を選びました。普段から Windows に慣れており、Windows のゲームやアプリも同じ PC で使うためです。ローカル LLM の推論だけなら Vulkan で目的を満たす場面もあります。

この選択には代償があります。Windows 版 ROCm は対応 GPU や機能が Linux 版より限定され、PyTorch や ComfyUI との組み合わせにも注意が必要です。

1. 利用するアプリケーションが対応するバックエンドを調べる
2. 対応 GPU とドライバーの組み合わせを確認する
3. Vulkan で足りる用途と、ROCm が必要な用途を分ける
4. 問題発生時に CPU 実行と比較できる構成を残す

## CPU は GPU を支える役割で選ぶ

GPU で推論するなら、最高性能の CPU は不要です。筆者は Core i5-14400 を選びました。発熱と消費電力を抑えやすく、手持ちの DDR4 を利用でき、内蔵グラフィックスを備えているためです。内蔵グラフィックスがあれば、ディスプレイ出力を計算用 GPU から切り離せます。

CPU の PCIe レーンとマザーボードの配線は、製品ページとマニュアルの両方で確認します。スロットの形状が x16 でも、電気的には x4 や x1 の場合があります。M.2 スロットを使うと、一部の PCIe スロットが無効になる製品もあります。

## PCIe レーンは形状と実効幅を分けて見る

採用したマザーボードには、GPU を挿せる x16 形状のスロットが複数あります。主に使う 2 本は、PCIe 4.0 x16 と PCIe 4.0 x4 です。

| 接続 | 片方向の理論帯域 |
| :-- | --: |
| <span class="nowrap">PCIe 4.0 x16</span> | 約 31.5 GB/s |
| <span class="nowrap">PCIe 4.0 x4</span> | 約 7.88 GB/s |

帯域には約 4 倍の差があります。しかし、推論中にモデルが VRAM へ載った後は、常に全モデルを PCIe 経由で転送するわけではありません。実際の影響は、モデルの分割方法、GPU 間転送、CPU オフロードの量で変わります。

筆者の用途では x4 側も問題なく利用できました。一方で、複数 GPU 間の peer copy が不安定要因になりました。帯域に加え、異なる接続幅の GPU 間で直接転送する実装の安定性も確認します。この問題は、第 4 章で llama.cpp のビルド設定として扱います。

## VRAM 容量を優先して Radeon を選ぶ

ローカル LLM で最初に不足しやすい資源は VRAM です。GPU の演算性能が高くても、モデルの多くが VRAM に収まらず RAM へ移れば、転送がボトルネックになります。筆者は、VRAM 容量に対する価格を重視し、Radeon AI PRO R9700 32 GB を 2 枚採用しました。

NVIDIA GPU は CUDA を前提とするソフトウェアが多く、導入の容易さと情報量で優位です。Radeon は同じ予算で大きな VRAM を確保できる場合がありますが、ROCm の対応確認と追加の調整が必要です。価格差は、調査と保守に使う時間との交換でもあります。

2 枚で合計 64 GB の VRAM があっても、常に 64 GB の単一 GPU と同じ動作にはなりません。容量と互換性を別々の評価項目にします。

## RAM は VRAM と同じくらい必要になる

モデルを GPU へ読み込む過程では、システムメモリにも大きな領域が必要です。OS、推論アプリ、モデルのマッピング、GPU へ載らないレイヤーも RAM を使います。筆者の経験では、RAM を VRAM の合計と同じ容量にするだけでは余裕がありません。

主検証機は、当初 96 GB だった RAM を 128 GB へ増設しました。目安は次のように考えます。

```text
必要 RAM ≒ モデルのファイルサイズ
          + CPU へオフロードする領域
          + OS とアプリケーションの領域
          + 読み込み・変換時の一時領域
```

これは厳密な式ではありません。モデル形式と実装で変わるため、タスクマネージャーなどでピーク値を計測します。仮想メモリは起動を成功させる場合があります。しかし、NVMe SSD への退避は RAM や VRAM より遅いため、安定運用の前提にはしません。

## ストレージ、電源、冷却

### ストレージ

量子化や用途ごとにモデルを保存すると、数百 GB はすぐに消費します。ComfyUI と MiniMax H3 の組み合わせも、モデル一式で約 50 GB です。容量だけでなく、初回読み込みと入れ替えの待ち時間を考え、NVMe SSD 2TB を利用します。

モデルは公式配布元から再取得できるため、すべてを Git やバックアップへ含めません。再取得元、ファイル名、ハッシュ、配置先を記録します。回線切断に備え、再開可能なダウンロード手段を用意します。

### 電源

R9700 は 1 枚あたり約 300 W の負荷を想定します。2 枚、CPU、ストレージ、ファンを同時に動かしても電源を定格上限へ張り付かせないよう、1000 W の電源を選びました。コネクターを分岐しすぎず、GPU メーカーが指定する本数と定格を満たすケーブルを使います。

定格電力の合計だけでなく、電源の品質、変換効率、瞬間的な負荷、ケーブルとコネクターの許容値を確認します。マルチ GPU の増設は、空きスロットだけを見て判断できません。

### 冷却

推論中は GPU の使用率が長時間高くなります。ゲームのように負荷が上下する処理とは、ケース内の温度傾向が異なります。GPU 間に吸気できる間隔を確保し、前面から背面への空気の流れを作ります。

筆者は温度センサーとサーマルカメラで推論中の温度を確認しましたが、今のところ問題はありません。また、ケースのサイドパネルが簡単に撮り外れるので、推論中はそれを外して、半オープンケースとして利用することもあります。

## 複数の検証機で性能を比較

ここで紹介した Radeon AI PRO R9700 x2 の構成以外にも、いくつかのパターンを組みました。ゲーム用のメイン PC、余剰パーツで組んだサブ PC、LLM 用に特化させた構成など、それぞれ異なる設計思想のマシンです。

各検証機において Ollama を利用して、次のモデルを同一プロンプトで 10 回実行しました。性能指標の token/sec の平均値を計測しました。

| モデル | パラメータ | 量子化 | サイズ |
| :-- | :-- | :-- | :-- |
| gemma4 [^gemma4-e4b] | 8B | <span class="nowrap">Q4_K_M</span> | 9.6 GB |
| qwen3.6 [^qwen3.6-35b] | 35B | <span class="nowrap">Q4_K_M</span> | 24 GB |

[^gemma4-e4b]: https://ollama.com/library/gemma4:e4b
[^qwen3.6-35b]: https://ollama.com/library/qwen3.6:35b

gemma4 は、どの GPU の VRAM にも収まるので、計算速度を比較します。qwen3.6 は VRAM に収まる・収まらないが起こるケースで、大きなモデルを選択したときのパフォーマンスを比較します。

| <span class="nowrap">構成</span> | A | B | C | D | E |
| :-- | :-- | :-- | :-- | :-- | :-- |
| CPU | Intel<br>i7 12700 | Ryzen<br>7 5700X | Ryzen<br>7 7700 | Intel<br>i7 13700 | Intel<br>i5 14400 |
| RAM | DDR4<br>64 GB | DDR4<br>64 GB | DDR5<br>32 GB | DDR5<br>32 GB | DDR4<br>128 GB |
| GPU | Intel<br>Arc B580<br>12 GB | Radeon<br>RX 9060 XT<br>16 GB | GeForce<br>RTX 5060 Ti<br>16 GB | GeForce<br>RTX 4070 Ti<br>12 GB | Radeon<br>AI PRO R9700<br>32 GB x2 |
| <b>計測結果</b> | (token/s) | | | | |
| gemma4<br>(9.6 GB) | 70.47 | 60.95 | 96.36 | 105.12 | 58.25 |
| qwen3.6<br>(24 GB) | 32.86 | 20.85 | 63.87 | 53.79 | 74.39 |

この表の E がここで紹介して検証機です。

LLM のモデルは VRAM にマウントされますが、同様に RAM にもマウントされます。たとえば 30 GB のモデルを読み込むと、VRAM と RAM はそれぞれ 30 GB 以上を消費します。また VRAM が十分なサイズではない場合、VRAM は RAM とモデルデータをやり取りするため、計算速度に影響します。

gemma4 はそのような速度低下が起こらない検証です。やはりというか、前世代とはいえど RTX 4070 Ti が勝利です。予想外として、まだ歴史が浅い Arc B580 が Radeon より速い結果は驚きでした。一方で qwen3.6 では、VRAM の大きさが結果に影響しました。計算が速い GeForce より、VRAM を多く積んだ AI PRO R9700 が勝ちました。

予想どおりというべきか、利用したいモデルに対して十分なサイズの VRAM を選択するのがよいです。多少不足する場合は、速度で挽回できるコアを選択しましょう。金額面から Arc が大穴でしょうか。なお、私は Radeon を愛用しています。

計算速度に関して評価しましたが、推論結果はどれも妥当な精度でした。この検証中で qwen3.6 に「Swift Concurrency について 200 文字で説明して」と質問した結果の一例を記載します。

```txt
Swift ConcurrencyはSwift 5.5で導入された現代的な並行処理モデルです。async/await構文により非同期処理を同期的な記法で直感的に実装でき、コールバック地獄を解消します。Actorによる共有状態の安全な保護と構造化並行処理を採用し、レースコンディションを防ぎながら高効率な並列実行を実現。ネットワーク通信からUI更新まで、複雑な処理も安全かつシンプルに扱えます。
```

## まとめ

ローカル LLM 検証機は、GPU の演算性能だけで設計できません。モデルの量子化後サイズから VRAM を決め、RAM、PCIe レーン、電源、冷却、ストレージを順に確認します。マルチ GPU は扱えるモデルを増やしますが、アプリケーションの対応と GPU 間転送が新しい不安定要因になります。

次章では、内部に 2 枚目の GPU を置けない小型 PC を、OCuLink で拡張します。接続帯域を落とすことで安定した事例から、最大速度だけを追わない検証方法を考えます。
