# ローカル LLM 検証機を設計する

自作 PC のパーツ選びは、予算内でもっとも高性能な製品を集めれば終わりではありません。ローカル LLM では、動かしたいモデルを VRAM に載せられるか、GPU と同程度の重みをシステムメモリでも扱えるか、複数の GPU を接続できるかが重要です。さらに、電源、冷却、日常用途との共存も考える必要があります。

筆者が検証機に定めた目標は、24 GB 以下で動く定番モデルを余裕を持って扱い、32〜50 GB 程度のモデルも試せることです。それを超えるモデルは、個人用 PC だけで無理に扱わず、クラウドを選びます。本章では、この目標から各パーツを選んだ過程を説明します。構成の元になった記録は Qiita で公開しています。[^qiita-pc]

[^qiita-pc]: [ローカル LLM 素人が作るローカル LLM 検証機](https://qiita.com/mitsuharu_e/items/92a3eccb65d9b5c4ceca)

## モデルから逆算する

最初に GPU の製品名を決めるのではなく、使いたいモデルの量子化後サイズを確認します。モデルファイルに加え、KV キャッシュと実行時バッファの余裕が必要です。32 GB のモデルファイルを 32 GB の VRAM へ載せる設計では、条件を少し変えただけで CPU へオフロードされます。

筆者は、検証範囲を次の 2 段階に分けました。

| 範囲 | モデルの目安 | 構成方針 |
| :-- | :-- | :-- |
| 日常利用 | VRAM 24 GB 以下 | 1 枚の GPU、または十分な余裕をもつ複数 GPU で円滑に動かす |
| 拡張利用 | VRAM 32〜50 GB | 複数 GPU へ分割し、速度より「動かせること」を優先する |

複数 GPU の VRAM は、すべてのアプリケーションで自動的にひとつの大きな領域になるわけではありません。推論エンジンがモデルのレイヤーを分割し、各 GPU へ配置できる必要があります。動画生成では 2 枚を搭載していても、実質的に 1 枚分の VRAM しか利用しない構成があります。用途ごとに対応状況を確認します。

## 検証機の構成

2026 年 8 月時点の主な構成は次のとおりです。新品だけでそろえず、以前の自作 PC からの流用品、中古品、アウトレット品も利用しました。ゲーム、画像生成、動画生成との兼用機です。

| パーツ | 構成 | 選定の軸 |
| :-- | :-- | :-- |
| OS | <span class="nowrap">Windows 11</span> | 日常利用するゲームやアプリとの共存 |
| CPU | <span class="nowrap">Intel Core i5-14400</span> | 内蔵 GPU、消費電力、DDR4 対応 |
| CPU クーラー | 120 mm 級空冷 | 扱いやすさと保守性 |
| マザーボード | <span class="nowrap">ASRock B760 Pro RS/D4 Wi-Fi</span> | PCIe スロット数、DDR4、LGA1700 |
| GPU | <span class="nowrap">Radeon AI PRO R9700</span> 32 GB × 2 | VRAM 容量と価格のバランス |
| RAM | <span class="nowrap">DDR4</span> 128 GB | GPU へ載せるモデルと OS の作業領域 |
| ストレージ | <span class="nowrap">NVMe SSD</span> | 大きなモデルの読み込みと入れ替え |
| 電源 | 1000 W、<span class="nowrap">80 PLUS Gold</span>、<span class="nowrap">ATX 3.1</span> | GPU 2 枚と瞬間的な負荷への余裕 |
| ケース | ATX 対応、通気重視 | 2 枚の GPU の冷却と作業性 |

## OS とバックエンドを先に考える

Radeon の計算基盤である ROCm は、Linux の対応範囲と情報量が充実しています。それでも筆者は Windows 11 を選びました。普段から Windows に慣れており、Windows のゲームやアプリも同じ PC で使うためです。ローカル LLM の推論だけなら Vulkan で目的を満たす場面もあります。

この選択には代償があります。Windows 版 ROCm は対応 GPU や機能が Linux 版より限定され、PyTorch や ComfyUI との組み合わせにも注意が必要です。「Radeon を使うなら必ず ROCm」と決めず、次の順で選びます。

1. 利用するアプリケーションが対応するバックエンドを調べる
2. 対応 GPU とドライバーの組み合わせを確認する
3. Vulkan で足りる用途と、ROCm が必要な用途を分ける
4. 問題発生時に CPU 実行と比較できる構成を残す

## CPU は GPU を支える役割で選ぶ

推論の大部分を GPU へオフロードするなら、最高性能の CPU が必須とは限りません。筆者は Core i5-14400 を選びました。発熱と消費電力を抑えやすく、手持ちの DDR4 を利用でき、内蔵グラフィックスを備えているためです。

内蔵グラフィックスがあれば、ディスプレイ出力を計算用 GPU から切り離せます。計算用 GPU の VRAM を画面描画に使わず、ドライバーや GPU の検証中も BIOS と Windows の画面を表示できます。これは、複数 GPU の一方が無効になった場合の復旧にも役立ちます。

CPU の PCIe レーンとマザーボードの配線は、製品ページとマニュアルの両方で確認します。スロットの形状が x16 でも、電気的には x4 や x1 の場合があります。M.2 スロットを使うと、一部の PCIe スロットが無効になる製品もあります。

## PCIe レーンは形状と実効幅を分けて見る

採用したマザーボードには、GPU を挿せる x16 形状のスロットが複数あります。主に使う 2 本は、電気的には PCIe 4.0 x16 と PCIe 4.0 x4 です。

| 接続 | 片方向の理論帯域 |
| :-- | --: |
| <span class="nowrap">PCIe 4.0 x16</span> | 約 31.5 GB/s |
| <span class="nowrap">PCIe 4.0 x4</span> | 約 7.88 GB/s |

帯域には約 4 倍の差があります。しかし、推論中にモデルが VRAM へ載った後は、常に全モデルを PCIe 経由で転送するわけではありません。実際の影響は、モデルの分割方法、GPU 間転送、CPU オフロードの量で変わります。

筆者の用途では x4 側も利用できました。一方で、複数 GPU 間の peer copy が不安定要因になりました。帯域に加え、異なる接続幅の GPU 間で直接転送する実装の安定性も確認します。この問題は、第 4 章で llama.cpp のビルド設定として扱います。

## VRAM 容量を優先して Radeon を選ぶ

ローカル LLM で最初に不足しやすい資源は VRAM です。GPU の演算性能が高くても、モデルの多くが VRAM に収まらず RAM へ移れば、転送がボトルネックになります。筆者は、VRAM 容量に対する価格を重視し、Radeon AI PRO R9700 32 GB を 2 枚採用しました。

NVIDIA GPU は CUDA を前提とするソフトウェアが多く、導入の容易さと情報量で優位です。Radeon は同じ予算で大きな VRAM を確保できる場合がありますが、ROCm の対応確認と追加の調整が必要です。価格差は、調査と保守に使う時間との交換でもあります。

2 枚で合計 64 GB の VRAM があっても、常に 64 GB の単一 GPU と同じ動作にはなりません。推論ではモデルを分割できますが、ComfyUI のワークフローによっては 1 枚だけを使います。また、アプリケーションによっては複数 Radeon でクラッシュしました。容量と互換性を別々の評価項目にします。

## RAM は VRAM と同じくらい必要になる

モデルを GPU へ読み込む過程では、システムメモリにも大きな領域が必要です。OS、推論アプリ、モデルのマッピング、GPU へ載らないレイヤーも RAM を使います。筆者の経験では、RAM を VRAM の合計と同じ容量にするだけでは余裕がありません。

主検証機は、当初 96 GB だった RAM を 128 GB へ増設しました。約 50 GB のモデルを扱うとき、64 GB の RAM では OS と周辺アプリの分が不足し、仮想メモリへの退避が起こりやすいためです。

目安は次のように考えます。

```text
必要 RAM ≒ モデルのファイルサイズ
          + CPU へオフロードする領域
          + OS とアプリケーションの領域
          + 読み込み・変換時の一時領域
```

これは厳密な式ではありません。モデル形式と実装で変わるため、タスクマネージャーなどでピーク値を計測します。仮想メモリは起動を成功させる場合があります。しかし、NVMe SSD への退避は RAM や VRAM より遅いため、安定運用の前提にはしません。

## ストレージ、電源、冷却

### ストレージ

量子化や用途ごとにモデルを保存すると、数百 GB はすぐに消費します。ComfyUI と MiniMax H3 の組み合わせも、モデル一式で約 50 GB です。容量だけでなく、初回読み込みと入れ替えの待ち時間を考え、NVMe SSD を利用します。

モデルは公式配布元から再取得できるため、すべてを Git やバックアップへ含めません。再取得元、ファイル名、ハッシュ、配置先を記録します。回線切断に備え、再開可能なダウンロード手段を用意します。

### 電源

R9700 は 1 枚あたり約 300 W の負荷を想定します。2 枚、CPU、ストレージ、ファンを同時に動かしても電源を定格上限へ張り付かせないよう、1000 W の電源を選びました。コネクターを分岐しすぎず、GPU メーカーが指定する本数と定格を満たすケーブルを使います。

定格電力の合計だけでなく、電源の品質、変換効率、瞬間的な負荷、ケーブルとコネクターの許容値を確認します。マルチ GPU の増設は、空きスロットだけを見て判断できません。

### 冷却

推論中は GPU の使用率が長時間高くなります。ゲームのように負荷が上下する処理とは、ケース内の温度傾向が異なります。GPU 間に吸気できる間隔を確保し、前面から背面への空気の流れを作ります。

筆者は温度センサーとサーマルカメラで確認しました。温度上昇の原因を切り分けるときは、サイドパネルを外した状態とも比較しました。ただし、開放すれば必ず冷えるとは限りません。設計された風の流れが失われ、ほこりや接触の危険も増えます。常用時はパネルを閉じた状態で温度を計測します。

## ベンチマークの読み方

複数の自作 PC で Ollama の推論速度を比較しました。構成全体が異なるため、GPU だけの厳密な比較ではありません。ここでは、個人が現実に使う PC 全体としての参考値です。

| 構成 | GPU | RAM | 小型モデルの実測 | 大型モデルの実測 |
| :-- | :-- | --: | --: | --: |
| A | <span class="nowrap">Intel Arc B580</span> 12 GB | 64 GB | 70.47 token/s | 32.86 token/s |
| B | <span class="nowrap">Radeon RX 9060 XT</span> 16 GB | 64 GB | 60.95 token/s | 20.85 token/s |
| C | <span class="nowrap">GeForce RTX 5060 Ti</span> 16 GB | 32 GB | 96.36 token/s | 63.87 token/s |
| D | <span class="nowrap">GeForce RTX 4070 Ti</span> 12 GB | 32 GB | 105.12 token/s | 53.79 token/s |
| E | <span class="nowrap">Radeon AI PRO R9700</span> 32 GB × 2 | 128 GB | 58.25 token/s | 74.39 token/s |

小型モデルでは GPU 1 枚の構成が速いこともあります。大型モデルでは、VRAM 容量の多い構成 E がもっとも速い結果でした。最高速度の比較前に、目的のモデルが GPU に収まるかを確認します。

計測には、同じモデルファイル、量子化、プロンプトを使います。コンテキスト長と推論エンジンのバージョンも固定します。初回だけモデル読み込みが含まれるため、ウォームアップ後に複数回計測します。

## 組み立て後の確認順

すべての GPU とアプリケーションを一度に導入すると、問題の場所が分かりません。次の順で確認します。

1. 内蔵グラフィックスだけで BIOS と Windows を起動する
2. GPU を 1 枚だけ接続し、ドライバーと負荷テストを確認する
3. 2 枚目を追加し、デバイスマネージャーで両方を確認する
4. 小さいモデルを CPU で実行する
5. 同じモデルを GPU 1 枚へオフロードする
6. 複数 GPU へ分割し、使用量と温度を記録する
7. 大きいモデルへ段階的に移る

各段階で構成とログを保存すれば、更新後に同じ試験を再実行できます。

## まとめ

ローカル LLM 検証機は、GPU の演算性能だけで設計できません。モデルの量子化後サイズから VRAM を決め、RAM、PCIe レーン、電源、冷却、ストレージを順に確認します。マルチ GPU は扱えるモデルを増やしますが、アプリケーションの対応と GPU 間転送が新しい不安定要因になります。

次章では、内部に 2 枚目の GPU を置けない小型 PC を、OCuLink で拡張します。接続帯域を落とすことで安定した事例から、最大速度だけを追わない検証方法を考えます。
